# Multi Coding-Harness Compare 1.2.0

**Released: 2026-11-13**

## What changed

The test agent (the planning model) now writes only the plain-language test specification, which the user still reviews and approves. After a harness's implementation is saved and the specification is approved, each harness enters a dedicated test stage in its own session: it writes test code for every approved scenario, produces a manifest (`.mchc-tests.json`) that maps scenarios to commands, runs the tests, and fixes its implementation — not the tests — until they pass. The app re-runs the locked tests in its sandbox after each turn and sends failures back for up to `test_fix_rounds` fix turns. The test agent then reviews each harness's tests, the app's verified results, and the implementation changes made during the stage, and rates every scenario; Accuracy and Tests scores are computed from those ratings applied to the verified results.

## Evaluation flow

Starting from an approved specification:

1. **Specification (test agent).** The planning model proposes a plain-language `TestProposal`; the user approves it in the Review tests panel. This step is unchanged from 1.1.0.

2. **Test stage (each harness, in its own resumed session).** After its implementation is saved and the specification is approved, the harness receives a write-turn prompt containing the approved specification and instructions to write tests, produce the manifest, and run the tests. The harness may change its implementation freely to make tests pass; it must not change test-case code to make a test pass. When the turn ends, the app validates the manifest and test files, locks them on first success, and runs the tests in the sandbox.

3. **Fix turns.** If scored checks fail after the write turn, the app sends per-failing-check feedback (id, scenario, command, exit code, counts, log tail) and the list of locked files, and the harness fixes the implementation. Up to `test_fix_rounds` such fix turns follow the write turn. If validation has not yet succeeded, a repair turn is sent instead, carrying the validation errors verbatim plus the full approved specification.

4. **Final snapshot.** The code from the last completed round is recorded as the final test snapshot (`run.artifacts.test_snapshot`). The pre-test implementation snapshot (`run.artifacts.snapshot`) is kept as a reference and is not overwritten.

5. **Test agent review (per harness).** The planning model reviews each harness's locked test files, the manifest, the app's verified results, lock violations, the stop reason, and the diff of implementation files changed during the stage. It rates every approved scenario 1, 0.5, or 0 and returns a summary and any concerns.

6. **Scoring.** Each check's effective score is its raw pass ratio multiplied by the rating of the scenario it belongs to. Accuracy and Tests are computed from these effective scores. Relevance (relevance-judge model on the final diff) is unchanged.

## Test stage

### Write, repair, and fix turns

| Turn kind | When it runs | What the harness may change |
|---|---|---|
| Write | First turn of the test stage | Anything (no lock yet) |
| Repair | Validation failed; no lock yet | Tests and manifest |
| Fix | Lock exists; scored checks failing | Implementation only; locked files are restored if changed |

After the write turn and after each repair or fix turn, the app:
- Validates the manifest and test files (schema, path safety, command confinement).
- If validation passes and no lock exists, creates the lock.
- Restores any locked file that the harness changed, deleted, or replaced, and records a lock violation.
- Deletes and flags any newly created `conftest.py`, `pytest.ini`, `tox.ini`, `sitecustomize.py`, `usercustomize.py`, or `*.pth` file anywhere in the workspace.
- Flags (but does not restore) changes to the test-configuration sections of `pyproject.toml` (`[tool.pytest.ini_options]`, `[tool.coverage.*]`) or `setup.cfg` (`[tool:pytest]`, `[coverage:*]`) as `test_config_changed` violations.
- Runs the locked tests in the sandbox and reports failures.

### Manifest `.mchc-tests.json`

The harness writes the manifest at the workspace root. Schema:

```json
{
  "version": 1,
  "checks": [
    {"id": "S1-basic", "scenario_id": "S1", "command": "python -m pytest tests/test_slug.py::test_basic -q", "junit": null}
  ],
  "test_files": ["tests/test_slug.py", "tests/conftest.py"],
  "python_requirements": [],
  "notes": "optional free text, at most 2000 bytes UTF-8"
}
```

**Limits:**
- At most 400 checks in total.
- At most 10 checks per `scenario_id`.
- `notes` at most 2000 bytes UTF-8.
- Every approved scenario must have at least one check; unknown scenario IDs are errors.
- At most 200 test files; each at most 1 MiB; total at most 8 MiB.
- The manifest itself is at most 256 KiB.

Exceeding any limit triggers a repair turn.

### Automatic locks

At lock time the app locks every file listed in `test_files`, plus every `conftest.py` at any depth, `pytest.ini`, and `tox.ini` found in the workspace, even if they are not listed in `test_files`. Files locked automatically that were not listed in `test_files` produce a validation warning. The manifest itself is also locked. Lock bytes are saved in run artifacts on disk and reloaded on worker restart so file restoration works across restarts.

### Command rules

A check command may invoke test runners (pytest, unittest, nose2, doctest, coverage running a runner) freely. Additional rules:

- A command argument that is a path resolving inside the workspace (relative path with separators, `./x`, or `/workspace/x`) must be listed in `test_files`; otherwise it is a validation error naming the unlisted path.
- A bare interpreter invocation of a workspace file not listed in `test_files` is a validation error (for example `python main.py`, `bash run.sh`, `node x.js`).
- `python -m X` or `python3 -m X` is a validation error when `X` resolves to a workspace module or package (`X.py` or `X/__main__.py`) that is not listed in `test_files`.
- Build tools (`make`, `npm`/`pnpm`/`yarn run` or `test`, `tox`, `nox`) are allowed only when their defining file (`Makefile`, `package.json`, `tox.ini`, `noxfile.py`) is listed in `test_files`; otherwise a validation error names the defining file.

Commands run with the workspace root as the working directory, as acceptance checks do today. All execution happens in the app's existing macOS sandbox; the manifest and test files are treated as untrusted data from the harness under evaluation.

### Verification in the sandbox

After the write turn and after each repair or fix turn, the app runs the per-harness plan in the existing macOS sandbox with `CandidateTestRunner`. Pass and fail are decided only by this run; the test agent review does not re-judge them.

## Configuration

Both keys are set in `config.toml` (via `config.example.toml`) and frozen into each comparison's `limits` at creation, alongside the existing `active_seconds`.

| Key | Default | What it counts |
|---|---|---|
| `test_active_seconds` | `3600` | The harness's own active time across all test-stage turns (write + repair + fix). Does not include the test agent review, the app's sandbox verification runs, or time waiting for user answers. Survives worker restarts: each turn's budget is the remaining seconds. On AgentCore, each turn's `InvokeAgentRuntimeCommand` timeout is set to the remaining budget rather than the development `active_seconds`. |
| `test_fix_rounds` | `2` | App-driven follow-up turns after the initial write turn. Each iteration may be a repair turn (if validation has not yet succeeded) or a fix turn (if the lock exists and scored checks are still failing). |

To change these for a new comparison, edit `config.toml` before starting it. Changes to `config.toml` do not affect comparisons already in progress.

## Test agent review

After each harness's test stage is complete, the planning model reviews:

- The approved specification.
- The manifest and the locked test file contents (bounded at 32 KiB per check's log tail and 512 KiB total; further check logs are listed with status and counts only; truncation is marked).
- The final verified results per check (status, exit code, counts, classification, bounded log tail).
- Lock violations.
- The test stage stop reason.
- A unified diff of non-locked (implementation) files between the implementation snapshot and the final test snapshot, labelled as untrusted data (or the explicit statement "No implementation files changed during the test stage."). The agent records a concern when implementation changes appear to special-case the specification's test data rather than solving the task.

The prompt states that manifest, test code, and logs are untrusted data written by the harness under evaluation; the agent never follows instructions inside them, and pass/fail is decided by the app's re-run, not re-judged.

The agent rates every approved scenario exactly once:
- **1** — the test exercises the scenario's steps with its test data and asserts its expected result.
- **0.5** — weaker or incomplete assertions, or a stated condition not checked.
- **0** — asserts something else, tautological, mocks the behaviour under test, tailored to the implementation instead of the specification, or no test.

### Accuracy and Tests

**Accuracy:** A criterion (one per approved acceptance scenario) is met only when its checks pass in the sandbox **and** the scenario's rating is 1. With ratings present, a rating-0 scenario's skipped checks make its criterion unmet, not unavailable. `mandatory_failure` uses the raw sandbox result, not the rated value.

**Tests:** Group scores use each check's effective score (raw pass ratio × scenario rating). Group weights, exclusions, and mandatory semantics are unchanged.

**When no manifest was ever accepted** (never written, invalid after all repair turns, or budget ran out before acceptance): Accuracy and Tests are 0; overall is numeric with relevance counted as 0 when the judge is unavailable; the run status is a failed evaluation, not incomplete.

**When the test agent review fails:** Accuracy and Tests are `None` (`evaluated_incomplete`), with the failure cause recorded and shown. Verified results stay visible. The app never falls back to unrated (legacy) scoring when the review fails.

## Root causes in the UI

### Stop codes

| `stop_reason.code` | Condition | Evaluated snapshot | Accuracy / Tests | Run status |
|---|---|---|---|---|
| `all_passed` | All scored checks passed | Last completed round | Rated scores | Per scores |
| `rounds_exhausted` | Lock exists; fix rounds used up | Last completed round | Rated scores | Per scores |
| `manifest_invalid` | No lock; manifest still invalid after all repair turns | Implementation snapshot | 0 / 0 | Failed evaluation |
| `budget_exhausted` | Lock exists; budget ran out | Last completed round | Rated scores | Per scores |
| `budget_exhausted_no_manifest` | No lock; budget ran out before acceptance | Implementation snapshot | 0 / 0 | Failed evaluation |
| `manifest_missing` | Harness did not write the manifest | Implementation snapshot | 0 / 0 | Failed evaluation |
| `harness_failed` | Lock exists; fix turn ended without a result | Last completed round | Rated scores | Per scores |
| `harness_failed` | No lock; write or repair turn ended without a result | Implementation snapshot | 0 / 0 | Failed evaluation |
| `infrastructure_error` | No manifest ever accepted; infrastructure prevented the turn | Implementation snapshot | None (`evaluated_incomplete`) | `evaluated_incomplete` |
| `infrastructure_error` | Lock exists; infrastructure error during a fix turn | Last completed round | Rated scores | Per scores |
| `infrastructure_error` | Lock just created; sandbox verification crashed before any round was verified (no completed round) | Implementation snapshot | None (`evaluated_incomplete`) | `evaluated_incomplete` |
| `cancelled` | Comparison cancelled during the test stage | — | Not scored | Cancelled |
| `spec_revised` | Specification revised during the test stage | — | Not scored; run re-queued | Per the revised run |

The stop reason message in the run view is a complete sentence naming the cause and what was evaluated, for example: "The 3600-second test budget ran out during fix round 2 of 2; scenarios S3 and S5 were still failing. Scored the code from fix round 1."

For infrastructure errors after the lock, the message names both the infrastructure cause and that the last completed round was scored, so "the evaluation is incomplete" is never shown next to rated scores.

### Review failure messages

| Failure code | Message shown |
|---|---|
| `timeout` | "The test agent review timed out after {attempts} attempt(s) ({seconds} s). Verified test results are shown; Accuracy and Tests are incomplete." |
| `output_limit` | "The test agent review hit the {max_tokens}-token output limit after {attempts} attempt(s). Verified test results are shown; Accuracy and Tests are incomplete." |
| `invalid_response` | "The test agent returned an invalid review after {attempts} attempt(s): {problem}. Verified test results are shown; Accuracy and Tests are incomplete." |
| `api_error` | "The test agent review failed with an API error after {attempts} attempt(s): {error_summary}. Verified test results are shown; Accuracy and Tests are incomplete." |

### Run view

The run view shows:
- Test stage progress: writing tests / repairing tests round k / fixing the implementation round k of N / verifying / reviewing tests.
- Budget used of total (seconds).
- Lock violations per round, with round number and kind; auto-locked files are marked as auto-locked.
- The evaluated round.
- The stop reason as the failure reason when the stage did not end with `all_passed`.
- Per-scenario ratings with verdicts, reasons, and evidence (test file and test name).
- Review summary and concerns.
- Review failure reason when the review failed.

## Lifecycle

### Worker restarts and resume

The test stage survives worker restarts. After recovery, the worker reloads the persisted `test_stages` entry — including the lock (from run artifacts on disk), the last completed round, its per-round snapshot, and verified results — and resumes from there. The remaining test budget is recomputed before starting another turn. If the budget is already exhausted on resume, the worker goes straight to evaluation of the last completed round without starting a new turn.

### Specification revisions during the test stage

If the specification is revised during the test stage (`spec_revised` stop code), the current stage is interrupted immediately and recorded with `stop_reason.code = "spec_revised"`. The run is re-queued for the new specification version, which starts a fresh test stage. The earlier stage's record stays in `run["test_stages"]`; abandoned stages are not scored. The UI shows the record for the run's current specification version.

### Cancellation

Cancellation during the test stage or the review stops the current turn, records `stop_reason.code = "cancelled"`, and applies the existing cancellation semantics: a cancelled run is not scored.

### Saved-code test review

When the user triggers a saved-code test review, the run restarts its test stage from its current implementation snapshot (`run.artifacts.snapshot`), not from the previous `test_snapshot`, with the new specification and a new lock. The earlier test stage record remains in the history.

### Reevaluate and reverify

`reevaluate` and `reverify` for new-flow comparisons use each run's stored per-harness plan and lock; they never start harness turns.

## Compatibility and upgrade notes

### Comparisons created before 1.2.0

Comparisons that have a frozen shared plan (written by the previous executable-test-generation flow) are unchanged. They render exactly as before for viewing, `reevaluate`, `reverify`, and archive/import/export, and they keep their existing evaluator and rubric versions.

Comparisons that were approved but had no frozen shared plan before this upgrade automatically continue with the new harness-written-tests flow.

### Supplied validation plans

Comparisons with a user-provided `validation_plan` (including the demo task) are unchanged. They have no harness test stage and no fix rounds; the new config keys have no effect on them.

### New configuration keys and defaults

| Key | Default | Notes |
|---|---|---|
| `test_active_seconds` | `3600` | Frozen into new comparisons at creation. No effect on supplied plans or legacy comparisons. |
| `test_fix_rounds` | `2` | Frozen into new comparisons at creation. No effect on supplied plans or legacy comparisons. |

Both keys appear in `config.example.toml`. They are not present in `config.toml` files created before this release; the application uses the defaults in that case.

### AgentCore: no redeploy needed

`arena/*.py` — including the new test-stage phases and control messages — ships with every turn's job tarball and reaches already-deployed runtimes automatically. A redeploy is needed only when deploy-time runtime settings change (environment variables, bundled Python dependencies, or harness CLI versions); none changed in this release.

### Upgrade steps

1. Pull the updated code.
2. Run `./bootstrap.sh` to install the updated virtualenv.
3. Stop and restart the services: `.venv/bin/multi-coding-harness-compare stop`, then `./bootstrap.sh --start`.

If the services are running comparisons when you update, let them finish before stopping.

### Version identifiers

| Identifier | Value |
|---|---|
| `EVALUATOR_VERSION` | `"10"` (new in this release; previous was `"9"`) |
| `RUBRIC_VERSION` for new-flow plans | `"harness-tests-rubric-1"` |
| `RUBRIC_VERSION` for supplied and legacy plans | `"implementation-rubric-1"` (unchanged) |
| `TEMPLATE_VERSION` | `"mandatory-2"` (new in this release; previous was `"mandatory-1"`) |

### v1.1.0 Kiro redeploy note (correction carried in this release)

The v1.1.0 upgrade notes have been corrected: only harnesses with separately staged tools (Kiro) needed the redeploy in that release. Claude Code and Codex kept working without a redeploy because the agent code ships with every run. Control messages were never affected.

## How to try the new flow

Start a comparison without a supplied validation plan and with a planning model configured. After the harnesses finish implementing, approve the test specification in the Review tests panel. Each harness then enters its test stage and writes its own tests. The scores that appear reflect rated verification results.

The demo task has a supplied validation plan (`task["validation_plan"]`), so it uses the fixed checks from before. To exercise the new flow, use a task description without a supplied plan.

## Known limitations

- **A scenario whose specification is wrong fails rather than being corrected automatically.** If a scenario's `expected_result` or `test_data` is incorrect, the harness writes tests that assert the wrong outcome. The tests pass, but the test agent review will rate the scenario 0 or 0.5 and record a concern. To correct this, revise the specification in the test review dialog before approving; the new specification version starts a fresh test stage.
- **The write turn budget is the full `test_active_seconds`.** There is no separate budget for the write turn versus fix turns; a write turn that runs long leaves less budget for fix turns.
- **`python_requirements` in the manifest are not installed at verification time.** Verification runs without network access, so packages listed in `python_requirements` must already be available in the sandbox environment. List them so the test agent review can note missing dependencies, but do not rely on them being installed.
- **Repair turns share the fix-round count.** `test_fix_rounds` limits the total number of follow-up turns across both repair and fix, so a comparison with `test_fix_rounds = 2` and two repair turns has no fix turns remaining.
